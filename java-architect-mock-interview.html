8:00–16:00

Technical / Architecture Depth

Goal: prove hands-on Java depth, not just buzzwords. Be ready to go one level deeper on anything you say.

Q3 — JVM / PERFORMANCE
INTERVIEWER

Tell me about a time you had to diagnose a JVM performance issue in production.

YOU

We had [symptom — e.g. periodic latency spikes / OOM errors] on [service]. I pulled heap dumps and GC logs and found [root cause — e.g. long G1GC pauses from an oversized young generation, or a memory leak from an unbounded cache]. I fixed it by [specific fix — tuning -Xmn/-XX:MaxGCPauseMillis, switching collectors, adding eviction policy], which brought p99 latency down from [X ms] to [Y ms].

Depth check: be ready for a follow-up like "why G1 over ZGC/Shenandoah?" — have a real opinion, not just the name of the collector you used.
Q4 — SPRING / DESIGN PATTERNS
INTERVIEWER

How do you think about dependency injection and Spring's role in keeping a large codebase maintainable?

YOU

DI is really about inverting control so components depend on abstractions, not concrete implementations — which is what makes large Spring codebases testable at scale. In practice, on [project], we enforced constructor injection over field injection everywhere, used interface-based beans so we could swap implementations per environment, and kept configuration externalized via @ConfigurationProperties rather than scattered @Value annotations. The bigger architectural point is that DI alone doesn't prevent a tangled dependency graph — we still had to actively manage module boundaries with [e.g. Spring Modulith / separate Maven modules] to stop services from silently coupling.

Q5 — DISTRIBUTED SYSTEMS
INTERVIEWER

How do you handle data consistency across microservices?

YOU

Depends on the boundary. For workflows that need strict consistency, I keep them inside a single service/transaction rather than splitting them. For cross-service workflows, we use [saga pattern with Kafka / orchestration vs choreography] — for example on [project], an order-fulfillment flow spanned [N] services, so we used an orchestrated saga with compensating transactions for rollback, and idempotency keys on each step so retries were safe. The trade-off is you accept eventual consistency and have to design the UI/business process around that.

Q6 — RAPID FIRE
INTERVIEWER

Quick ones — circuit breaker vs. retry, when do you reach for each? And REST vs. gRPC for internal service calls?

YOU
  • Retry for transient failures you expect to self-resolve quickly; circuit breaker (e.g. Resilience4j) to stop hammering a failing downstream and let it recover — I use both together, retry inside the breaker's closed state.
  • REST when the consumer is external, human-debuggable, or polyglot clients matter. gRPC internally when we need lower latency and strict contracts via protobuf — we moved [specific internal path] to gRPC and cut serialization overhead noticeably.
Timing check: keep rapid-fire answers under 20 seconds each — this segment tests reflexes, not essays.
16:00–23:00

System Design Scenario

Goal: state assumptions out loud, structure the design, and defend trade-offs when pushed.

DESIGN PROMPT
INTERVIEWER

Let's do a quick design exercise. Design a notification service that needs to send emails, SMS, and push notifications, at high volume, with retries and delivery tracking. How would you approach it?

YOU

Before I sketch anything — a couple of assumptions: I'll assume peak volume around [X notifications/sec], that delivery ordering doesn't strictly matter, and that we need at-least-once delivery with dedup on the client side. Tell me if that's off.

At a high level: an API layer accepts notification requests and publishes them to a Kafka topic partitioned by [tenant/user ID]. Separate consumer groups per channel — email, SMS, push — each with their own worker pool, so a slowdown in one channel (say, an SMS provider outage) doesn't back up the others. Each worker calls the relevant provider, writes delivery status to a status store, and on failure pushes to a dead-letter topic with exponential backoff retry. For tracking, I'd expose a delivery-status API backed by that status store, and emit metrics per channel for observability.

FOLLOW-UP PUSHBACK
INTERVIEWER

Why Kafka instead of a simpler queue like SQS or RabbitMQ?

YOU

Fair question — for pure task queuing, SQS or RabbitMQ would honestly be simpler and I wouldn't rule them out. I'd lean Kafka specifically because we also want a durable, replayable log — if a provider integration has a bug and we need to reprocess a day's worth of notifications, Kafka's retention makes that straightforward, whereas a traditional queue discards messages once consumed. If replay wasn't a requirement, I'd probably default to something lighter-weight.

Why this matters: notice the answer doesn't defend Kafka dogmatically — it states the real reason and concedes the alternative would work too. That's the "committed but not defensive" tone architects are evaluated on.
FOLLOW-UP SCALE
INTERVIEWER

What happens if one downstream provider (say, the SMS vendor) starts rate-limiting you hard?

YOU

That's exactly why the consumer groups are split per channel — the SMS consumer pool backs up on its own topic, doesn't affect email or push. I'd add a circuit breaker around the SMS provider client so once we see a threshold of 429s, we stop hammering it and let messages queue in Kafka rather than burning through retries. We'd also want an alert on consumer lag for that topic so on-call knows it's happening, not just silently degrading.
