Java → Docker → Kubernetes on Azure: 2-Hour Deployment Lab

Build it → deploy it → access it → break it → troubleshoot it → understand it → clean it up.

You already know Java/Spring/Docker basics. This lab skips app development entirely and focuses purely on the deployment pipeline, using a pre-built sample-app.jar (Spring Boot, exposes GET /hello on port 8080).

PART 1 — Dockerfile

Expected layout:

sample-app/
 ├── sample-app.jar
 └── Dockerfile

STEP 1 — Write the Dockerfile

Goal: package the JAR into a runnable image. Why: Docker gives a portable, identical runtime everywhere (laptop, VM, cluster).

# Dockerfile
FROM eclipse-temurin:17-jre-jammy
WORKDIR /app
COPY sample-app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Line by line: - FROM eclipse-temurin:17-jre-jammy — small JRE-only base image (no JDK bloat needed to run a JAR). Match this to whatever Java version your JAR was built with. - WORKDIR /app — creates/enters /app inside the image; later paths are relative to it. - COPY sample-app.jar app.jar — copies your JAR from build context into the image, renamed for a stable entrypoint path. - EXPOSE 8080 — documentation only (doesn't actually publish the port; -p at docker run does that). - ENTRYPOINT [...] — the command that runs when the container starts.

Checkpoint: Dockerfile and sample-app.jar sit side by side.

PART 2 — Build & Run Locally

STEP 2 — Build the image [LOCAL MACHINE]

docker build -t sample-java-app:1.0 .
docker images

What happened: Docker read the Dockerfile, layered each instruction into an image, tagged it sample-java-app:1.0. Common problem: "no such file" → you're not in the sample-app/ directory.

STEP 3 — Run it [LOCAL MACHINE]

docker run -d -p 8080:8080 --name sample-app-local sample-java-app:1.0
docker ps
curl http://localhost:8080/hello

What happened: Docker created a container from the image, mapped host port 8080 → container port 8080. Checkpoint: curl returns a response.

STEP 4 — Stop/remove [LOCAL MACHINE]

docker stop sample-app-local
docker rm sample-app-local

You've now proven: JAR → Dockerfile → Image → Container works. Everything after this is about getting that same image running on Azure.

PART 3 — Create the Azure VM (Portal-first)

STEP 5 — Create VM via Azure Portal

Goal: a small Ubuntu VM to act as our "server."

Portal Action: 1. Portal → Create a resource → Virtual Machine 2. Resource Group: create new, e.g. rg-k8s-lab — a logical container so you can delete everything in one action later. 3. Region: pick nearest to you (affects latency + cost). 4. VM name: vm-k8s-lab 5. Image: Ubuntu Server 22.04 LTS — free, well-documented, k3s-friendly. 6. Size: Standard_B1s or B2s (B2s recommended — k3s + Docker is tight on 1GB RAM). Burstable/cheap tier, fine for a lab. 7. Authentication: SSH public key (generate new key pair, download the .pem). 8. Inbound port rules: allow SSH (22) now; we'll add 8080 and 6443 later once we know we need them — least-privilege by default. 9. Disks: default Standard SSD is fine. 10. Review + Create.

Why each piece exists: - Resource Group = a folder for billing/lifecycle — delete it, everything inside dies with it. - NSG (Network Security Group) = a firewall attached to the VM's network interface; nothing reaches the VM unless a rule allows it. - Public IP = the address the internet uses to reach your VM.

Equivalent CLI (optional):

az group create --name rg-k8s-lab --location uksouth
az vm create --resource-group rg-k8s-lab --name vm-k8s-lab \
  --image Ubuntu2204 --size Standard_B2s \
  --admin-username azureuser --generate-ssh-keys

Checkpoint: deployment succeeds, note the Public IP shown on the VM overview page.

STEP 6 — SSH in [LOCAL MACHINE]

chmod 400 vm-k8s-lab_key.pem
ssh -i vm-k8s-lab_key.pem azureuser@<AZURE_PUBLIC_IP>

[AZURE VM]

uname -a
lsb_release -a

What happened: your terminal is now a shell running on the VM, not your laptop. Every command from here labeled [AZURE VM] runs there. Common problem: "permission denied (publickey)" → wrong key file or wrong username (azureuser unless you changed it).

PART 4 — Docker on the VM

STEP 7 — Install Docker [AZURE VM]

sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io
sudo usermod -aG docker $USER
newgrp docker

STEP 8 — Verify [AZURE VM]

docker --version
docker run hello-world
  • Docker daemon = background service managing images/containers.
  • Docker CLI = the docker command you type, which talks to the daemon.
  • Registry = a place images are stored/pulled from (Docker Hub, ACR, etc.) — needed next, since your laptop's local image doesn't magically exist on the VM.

Checkpoint: hello-world prints its "Hello from Docker!" message.

PART 5 — Get the Image onto the VM (via Azure Container Registry)

The VM cannot see the image sitting on your laptop's Docker daemon — it needs to pull it from somewhere reachable. ACR is the simplest realistic option here.

STEP 9 — Create ACR [LOCAL MACHINE, Portal or CLI]

az acr create --resource-group rg-k8s-lab --name <REGISTRY_NAME> --sku Basic
az acr login --name <REGISTRY_NAME>

(Portal equivalent: Create a resource → Container Registry → same resource group → Basic SKU.)

STEP 10 — Push the image [LOCAL MACHINE]

docker tag sample-java-app:1.0 <REGISTRY_NAME>.azurecr.io/sample-java-app:1.0
docker push <REGISTRY_NAME>.azurecr.io/sample-java-app:1.0

STEP 11 — Let the VM pull from ACR [AZURE VM]

az acr login --name <REGISTRY_NAME>   # requires az cli on VM, or use --username/--password with docker login
docker login <REGISTRY_NAME>.azurecr.io -u <USERNAME> -p <PASSWORD>
docker pull <REGISTRY_NAME>.azurecr.io/sample-java-app:1.0

(Simplest auth path for a lab: Portal → your ACR → Access keys → enable Admin user → use that username/password with docker login.)

Flow recap:

Local build --push--> ACR --pull--> VM

Checkpoint: docker images on the VM shows the image.

PART 6 — Run Directly on the VM (pre-Kubernetes)

STEP 12 [AZURE VM]

docker run -d -p 8080:8080 --name sample-app <REGISTRY_NAME>.azurecr.io/sample-java-app:1.0

Now add an NSG inbound rule for port 8080 (Portal → VM → Networking → Add inbound port rule → 8080, TCP).

STEP 13 — Test from your laptop [LOCAL MACHINE]

curl http://<AZURE_PUBLIC_IP>:8080/hello

Trace:

Internet → Azure Public IP → NSG (allows 8080) → VM NIC → Docker container (port 8080) → Java app

This is deliberately the pre-Kubernetes baseline — one container, no self-healing, no scaling. Kubernetes exists to solve what this setup lacks.

Cleanup before moving on: docker stop sample-app && docker rm sample-app (Kubernetes will run it instead).

PART 7 — Why Kubernetes?

docker run gives you exactly one container with no supervision — if it crashes, it stays dead; to scale, you SSH in and run more docker run commands by hand; there's no built-in load balancing or self-healing.

Concept What it is Where it appears here
Cluster The whole set of machines running Kubernetes Our single VM (acting as the whole cluster)
Node One machine in the cluster The VM itself
Pod Smallest deployable unit; wraps ≥1 container Wraps your sample-java-app container
Deployment Declares "run N replicas of this Pod, keep them healthy" deployment.yaml below
ReplicaSet Created by the Deployment; maintains replica count Managed automatically
Service Stable network endpoint routing to Pods service.yaml below
Namespace Logical partition of a cluster We'll use default

PART 8 — Install k3s

STEP 14 [AZURE VM]

curl -sfL https://get.k3s.io | sh -
sudo k3s kubectl get nodes

Why k3s: it's a single ~50MB binary bundling a full Kubernetes control plane + kubelet, purpose-built for small/edge/single-node setups like this VM — installing full upstream Kubernetes (kubeadm, etc.) is overkill for a 2-hour lab.

Make kubectl easier to use:

mkdir -p ~/.kube
sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
sudo chown $USER ~/.kube/config
alias kubectl='k3s kubectl'   # or: sudo cp /usr/local/bin/k3s /usr/local/bin/kubectl
kubectl get nodes

Expected output: one node, STATUS: Ready. This confirms the control plane and kubelet are both healthy and talking to each other.

PART 9 — Kubernetes Deployment

Because k3s runs on the VM, it can pull straight from the same ACR — you still need to authenticate it (a Secret), since k3s has no memory of your earlier docker login.

STEP 15 — Create the ACR pull secret [AZURE VM]

kubectl create secret docker-registry acr-secret \
  --docker-server=<REGISTRY_NAME>.azurecr.io \
  --docker-username=<USERNAME> --docker-password=<PASSWORD>

STEP 16 — deployment.yaml

apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-java-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: sample-java-app
  template:
    metadata:
      labels:
        app: sample-java-app
    spec:
      imagePullSecrets:
        - name: acr-secret
      containers:
        - name: sample-java-app
          image: <REGISTRY_NAME>.azurecr.io/sample-java-app:1.0
          ports:
            - containerPort: 8080
  • replicas: 2 — Kubernetes keeps 2 Pods running; kill one and it's replaced automatically.
  • selector/labels — how the Deployment finds/owns "its" Pods.
  • imagePullSecrets — lets the kubelet authenticate to ACR.
  • containerPort: 8080 — documents the port the app listens on inside the Pod.

STEP 17 — Apply & verify [AZURE VM]

kubectl apply -f deployment.yaml
kubectl get deployments
kubectl get pods
kubectl describe pod <pod-name>

What happened: the Deployment controller created a ReplicaSet, which created 2 Pods; the kubelet on the node pulled the image and started the containers. Checkpoint: both pods show STATUS: Running.

PART 10 — Kubernetes Service

A Pod's IP is ephemeral (it changes if the Pod restarts) — a Service gives a stable way in.

STEP 18 — service.yaml

apiVersion: v1
kind: Service
metadata:
  name: sample-java-app-svc
spec:
  type: NodePort
  selector:
    app: sample-java-app
  ports:
    - port: 8080
      targetPort: 8080
      nodePort: 30080

NodePort exposes the app on <node-ip>:30080 — simplest option for a single-node lab (no cloud LoadBalancer needed).

kubectl apply -f service.yaml
kubectl get services

Open NSG inbound port 30080 (same as Step 12's process).

Flow: Pod → Service (routes by label selector, load-balances across replicas) → external access via NodePort.

STEP 19 — Test [LOCAL MACHINE]

curl http://<AZURE_PUBLIC_IP>:30080/hello

PART 11 — Trace the Full Request

curl http://<AZURE_PUBLIC_IP>:30080/hello
  1. Client → Azure Public IP — DNS/IP routing gets the packet to Azure's edge.
  2. NSG — checks the inbound rule allowing TCP 30080; drops it otherwise.
  3. Azure VM (NIC) — packet arrives at the node's network interface.
  4. kube-proxy (part of k3s) — intercepts traffic to NodePort 30080, rewrites it toward one of the Service's healthy Pod IPs (round-robin across your 2 replicas).
  5. Service → Pod — traffic reaches the selected Pod's IP:8080.
  6. Pod → Container — the Pod's network namespace hands the packet to the container process.
  7. Java/Spring Boot — Tomcat (embedded) accepts the HTTP request, routes it to your /hello controller.
  8. Response — travels back the same path in reverse.

PART 12 — Troubleshooting Drill

Problem 1: Pod not running

kubectl get pods
kubectl describe pod <pod-name>
kubectl logs <pod-name>

describe shows Events (e.g. ImagePullBackOff, CrashLoopBackOff); logs shows app-level stdout/stderr.

Problem 2: App unreachable despite Running pods

kubectl get svc
kubectl describe svc sample-java-app-svc
kubectl get pods -o wide

Check in order: does the Service's selector match the Pod's labels? Is the NSG rule actually present for the NodePort? Is anything else already bound to that port on the VM (sudo ss -tulpn)?

Problem 3: Image pull failure

kubectl describe pod <pod-name>   # look for "ImagePullBackOff" / "ErrImagePull"

Check: is <REGISTRY_NAME>.azurecr.io/sample-java-app:1.0 spelled exactly right (typo'd tags are the #1 cause)? Is acr-secret referenced correctly in imagePullSecrets? Has the ACR admin password changed/rotated?

PART 14 — Cleanup

Kubernetes [AZURE VM]

kubectl delete -f service.yaml
kubectl delete -f deployment.yaml

Docker [AZURE VM / LOCAL]

docker system prune -a   # removes unused images/containers on both sides if desired

Azure — the important one

az group delete --name rg-k8s-lab --yes --no-wait

Deleting the resource group removes the VM, its disk, public IP, NSG, and the ACR together — the single action that stops all billing for this lab. Verify in the Portal that the resource group is actually gone, not just "deleting."

Can I Explain This in an Interview?

Q1: What's the difference between a Docker image and a container? An image is an immutable, layered filesystem + metadata; a container is a running (or stopped) instance of that image with its own writable layer and process namespace.

Q2: Why did you need a container registry instead of copying the image file directly? The Azure VM's Docker/kubelet daemon has no access to your laptop's local image store; a registry is the standard, repeatable way to distribute images across machines, and it's what Kubernetes' image-pull mechanism expects.

Q3: What does a Kubernetes Deployment actually manage? It manages a ReplicaSet, which in turn ensures the desired number of identical Pods are running; if a Pod dies, the ReplicaSet controller creates a replacement to reconcile actual state with desired state.

Q4: Why use a Service instead of hitting a Pod's IP directly? Pod IPs are ephemeral and change on restart/rescheduling; a Service provides a stable virtual IP/DNS name and load-balances across all matching Pods via label selectors.

Q5: What's the difference between NodePort, ClusterIP, and LoadBalancer Services? ClusterIP is internal-only; NodePort additionally exposes a static port on every node's IP (what we used, since there's no cloud load balancer on a bare VM); LoadBalancer provisions a cloud provider's external load balancer (used with AKS, not this setup).

Q6: Why k3s instead of full Kubernetes or AKS for this lab? k3s is a single lightweight binary suited to a single-node/edge scenario and installs in under a minute, letting the lab focus on core Kubernetes concepts rather than control-plane HA or AKS-specific tooling.

Q7: How would you debug a Pod stuck in CrashLoopBackOff? kubectl logs <pod> (add --previous if it already restarted) to see the app's exit reason, and kubectl describe pod for OOMKilled/Events; the root cause is almost always inside the container process itself, not Kubernetes.

Q8: What is an NSG and why is it necessary even though the app has its own port config? The NSG is a network-layer firewall at the Azure infrastructure level, entirely separate from anything the OS or app does; a port can be "listening" inside the VM and still be completely unreachable if the NSG doesn't allow it.

Q9: What would you change to make this production-appropriate? Move to AKS for a managed control plane and real LoadBalancer/Ingress support, add TLS, use a proper secrets manager instead of a plain Secret object, add CI/CD instead of manual docker build/kubectl apply, and add resource limits/requests and health probes.

Q10: Walk me through what happens end-to-end when a client hits your endpoint. (Use the Part 11 hop-by-hop trace: Public IP → NSG → VM NIC → kube-proxy/NodePort → Service → Pod → container → Spring Boot controller → response retraces the path.)
