Introduction & the Modern Java Landscape

1.1 Why This Book, Why Now

Java has been declared "dying" more times than any language in computing history, and each time it has responded by quietly becoming more capable, more concurrent, and more comfortable running the systems that a modern economy actually depends on. In 2026 that pattern holds again. The language has just absorbed a decade's worth of overdue modernisation — virtual threads, pattern matching, records, structured concurrency — while the ecosystem around it, led by Spring Boot 4 and a new generation of cloud-native runtimes, has caught up with what containers, Kubernetes and large language models now expect of a backend platform.

This book exists because most Java material still teaches the Java of 2015: heavyweight application servers, verbose configuration, thread pools tuned by trial and error, and a vague awareness that "reactive" exists somewhere over the horizon. That material will not prepare you for a technical interview at a UK bank, a government digital service, or a consultancy in 2026. This book will. Every chapter is built around code you can run today, on the versions of Java and Spring that are actually being deployed, with the operational concerns — cost, compliance, observability — that separate a working prototype from something you'd trust with real money or real citizens' data.

1.2 Java in 2026: Still the Backbone of Enterprise Britain

Walk into the engine room of almost any UK high-street bank, insurer, or central government department and you will find Java. Not because nobody has considered alternatives, but because Java's combination of a mature, backward-compatible platform, a colossal library ecosystem, predictable long-term support, and a workforce that already knows it makes it the least risky choice for systems that must run for decades and cannot fail quietly.

Three structural facts keep Java at the centre of UK enterprise technology in 2026:

  • Long-Term Support cadence. Java 21 (September 2023) and Java 25 (September 2025) are both LTS releases, meaning vendors commit to years of security patches. Enterprises that were stuck on Java 8 for a decade now have a much shorter, well-lit path to modern language features every two years, without the churn of adopting every six-monthly release.
  • The Spring ecosystem's continued dominance. Spring Boot remains the default choice for the overwhelming majority of new Java services in UK job postings, and Spring Boot 4 (built on Spring Framework 7) has been engineered specifically around virtual threads, native image support and AI integration — closing gaps that previously pushed cloud-native teams toward Quarkus or Micronaut.
  • Regulatory gravity. Financial services and the public sector — two of the largest employers of Java developers in the UK — operate under heavy compliance requirements (PRA/FCA regulation, GDPR, Government Digital Service standards). These sectors prize platforms with mature auditing, strong typing, and long support windows over the fashionable new framework of the month. Java, and the JVM's tooling for security and observability, fits that risk profile extremely well.
Field note. A useful mental model: Java rarely wins in domains where developer velocity for greenfield experimentation is the only variable that matters. It wins overwhelmingly wherever correctness, auditability and multi-decade maintainability matter as much as speed of initial delivery — which describes most of the UK's regulated industries.

1.4 What's New Since Java 8/11: A Fast-Forward Tour

If your most recent hands-on Java experience stopped around Java 8 or 11, here is the essential map of what has changed, condensed into the features that actually show up in modern codebases and interviews. We cover each of these in full depth in Chapter 2; this section is your orientation.

1.4.1 Records — Data Carriers Without the Boilerplate

public record Money(BigDecimal amount, Currency currency) {
    public Money {
        if (amount.scale() > currency.getDefaultFractionDigits()) {
            throw new IllegalArgumentException("Too many decimal places for " + currency);
        }
    }

    public Money plus(Money other) {
        if (!currency.equals(other.currency)) {
            throw new IllegalArgumentException("Currency mismatch");
        }
        return new Money(amount.add(other.amount), currency);
    }
}

A record generates the constructor, accessors, equals, hashCode and toString for you, while still allowing validation logic in a compact canonical constructor as shown above. In enterprise codebases, records have largely replaced hand-written DTOs and value objects.

1.4.2 Sealed Classes and Pattern Matching

public sealed interface PaymentEvent permits PaymentInitiated, PaymentSettled, PaymentFailed {}

public record PaymentInitiated(String reference, Money amount) implements PaymentEvent {}
public record PaymentSettled(String reference, Instant settledAt) implements PaymentEvent {}
public record PaymentFailed(String reference, String reason) implements PaymentEvent {}

String describe(PaymentEvent event) {
    return switch (event) {
        case PaymentInitiated(var ref, var amount) -> "Initiated " + ref + " for " + amount;
        case PaymentSettled(var ref, var at) -> "Settled " + ref + " at " + at;
        case PaymentFailed(var ref, var reason) -> "Failed " + ref + ": " + reason;
    };
}

Sealed types close the set of permitted subtypes, and the compiler enforces exhaustiveness in the switch above — if a new event type is added and a branch is not, compilation fails. Combined with record patterns, this gives Java much of the type-safety experience developers associate with functional languages, without leaving the JVM.

1.4.3 Virtual Threads — The End of Reactive-by-Necessity

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> futures = orders.stream()
        .map(order -> executor.submit(() -> processOrder(order)))
        .toList();

    for (Future<String> future : futures) {
        System.out.println(future.get());
    }
}

Virtual threads, finalised in Java 21, let you write simple, blocking-style code — one thread per request — while the JVM multiplexes millions of virtual threads onto a small pool of OS threads. For most CRUD and I/O-bound enterprise services, this removes the need to adopt reactive programming purely for scalability. We dedicate a full section of Chapter 2 to when virtual threads are the right tool and where reactive streams (WebFlux, Project Reactor) still earn their complexity.

1.4.4 Structured Concurrency

Structured concurrency treats a group of related concurrent tasks as a single unit of work, so that if one subtask fails, siblings are cancelled automatically and errors propagate predictably — replacing hand-rolled CompletableFuture orchestration that was a frequent source of subtle bugs.

1.4.5 Project Valhalla: Value Objects

Value objects (evolving through preview stages into Java 25/26) let the JVM lay out simple, immutable data types without object headers or pointer indirection — closing a long-standing performance gap with languages that support true value types, and mattering directly for high-throughput financial and data-processing workloads.

1.4.6 The Vector API

The incubating/finalising Vector API lets Java code express data-parallel computations that compile down to CPU SIMD instructions, relevant for analytics, machine-learning pre/post-processing and numerically heavy financial calculations run directly on the JVM rather than shelled out to native code.

Orientation summary. If you remember five words from this section: records, sealed types, virtual threads, structured concurrency, Valhalla. Everything else in modern Java either supports or builds on these five ideas.

Java Language Mastery

This chapter is the technical foundation for everything that follows. Every later chapter — Spring Boot services, cloud-native deployments, AI agents, resilient microservices — is written using the language features covered here. If you take one chapter slowly, take this one. We move from data modelling (records, sealed classes, pattern matching) through the concurrency model that has genuinely changed how Java services are architected (virtual threads, structured concurrency), and finish with the two forward-looking capabilities most relevant to performance-sensitive UK enterprise work: Valhalla value objects and the Vector API.

2.1 Records and Data-Oriented Programming

Records, finalised in Java 16 and now deeply idiomatic by 2026, are Java's answer to a problem every enterprise codebase has: an overwhelming number of small, immutable classes that exist purely to carry data — DTOs, value objects, API request/response shapes, event payloads. Before records, each one demanded a constructor, getters, equals, hashCode, and toString, typically generated by an IDE and then never looked at again, but still adding maintenance surface and diff noise.

public record CustomerAccount(
        String accountNumber,
        String sortCode,
        BigDecimal balance,
        AccountStatus status) {

    // Compact canonical constructor: validation only, no field assignment needed
    public CustomerAccount {
        if (sortCode == null || !sortCode.matches("\\d{2}-\\d{2}-\\d{2}")) {
            throw new IllegalArgumentException("Invalid UK sort code: " + sortCode);
        }
        if (balance.scale() > 2) {
            throw new IllegalArgumentException("Balance must not exceed 2 decimal places");
        }
    }

    // Additional instance methods are allowed
    public boolean isOverdrawn() {
        return balance.signum() < 0;
    }

    // Static factory methods are common alongside records
    public static CustomerAccount openWith(String accountNumber, String sortCode) {
        return new CustomerAccount(accountNumber, sortCode, BigDecimal.ZERO, AccountStatus.ACTIVE);
    }
}

Three properties make records more than syntactic sugar:

  • Structural equality is free. Two CustomerAccount instances with identical field values are equals(), which matters constantly in tests and in collections/sets of domain objects.
  • Immutability is the default. All fields are implicitly final. This eliminates an entire category of concurrency bugs, which becomes especially relevant once virtual threads make it cheap to run enormous numbers of concurrent tasks (Section 2.4).
  • They compose naturally with pattern matching, covered in Section 2.3 — record patterns let you destructure a record directly in a switch or instanceof.
Best practice. Use records for anything that is fundamentally "a bag of values with no identity beyond its content": API payloads, events, query results, configuration snapshots. Keep using ordinary classes for entities with a persistent identity and mutable lifecycle (e.g. a JPA @Entity tracked by Hibernate) — records and JPA entities do not mix well, because JPA expects mutable, identity-based objects with a no-args constructor.

2.1.1 Records Implementing Interfaces

public interface Auditable {
    Instant createdAt();
}

public record LoanApplication(
        String applicantId,
        BigDecimal requestedAmount,
        Instant createdAt) implements Auditable {}

Records can implement interfaces (but cannot extend another class, since they implicitly extend java.lang.Record), which is enough for most data-modelling needs while keeping the door open for shared behavioural contracts.

2.2 Sealed Classes and Exhaustive Pattern Matching

Sealed classes, finalised in Java 17, let a type author declare exactly which classes or interfaces are permitted to extend or implement a type. Combined with pattern matching, this gives Java compiler-enforced exhaustiveness — a capability enterprise Java developers previously had to simulate with enums plus a lot of discipline.

public sealed interface ClaimDecision
        permits ClaimApproved, ClaimRejected, ClaimPendingReview {}

public record ClaimApproved(String claimId, BigDecimal payoutAmount) implements ClaimDecision {}
public record ClaimRejected(String claimId, String reasonCode) implements ClaimDecision {}
public record ClaimPendingReview(String claimId, List<String> outstandingDocuments) implements ClaimDecision {}

Because the interface is sealed with an explicit permits clause, the compiler knows the complete set of implementing types at compile time. A switch expression over a sealed type does not need a default branch — and, crucially, if a new subtype is ever added, every exhaustive switch over that type across the entire codebase fails to compile until it is updated:

String toCustomerMessage(ClaimDecision decision) {
    return switch (decision) {
        case ClaimApproved(var id, var amount) ->
            "Claim " + id + " approved for £" + amount;
        case ClaimRejected(var id, var reason) ->
            "Claim " + id + " was not approved: " + reason;
        case ClaimPendingReview(var id, var docs) ->
            "Claim " + id + " needs: " + String.join(", ", docs);
    };
}
UK Job Market Tip. Sealed classes plus exhaustive switch expressions are a favourite whiteboard/live-coding topic in senior Java interviews at UK fintechs, because they test whether a candidate understands compiler-enforced correctness rather than relying on discipline and code review. Be ready to explain, with an example, why this is safer than a traditional enum-plus-if-chain.

2.3 Pattern Matching for switch and Record Patterns

instanceof pattern matching (Java 16) and switch pattern matching (finalised Java 21) together eliminate the classic "check the type, then cast" boilerplate:

// Before: check-then-cast
if (event instanceof PaymentFailed) {
    PaymentFailed failed = (PaymentFailed) event;
    log.warn("Payment {} failed: {}", failed.reference(), failed.reason());
}

// After: pattern variable bound directly
if (event instanceof PaymentFailed failed) {
    log.warn("Payment {} failed: {}", failed.reference(), failed.reason());
}

Record patterns go a step further, destructuring nested records inline, including guarded patterns with when clauses for conditional matching:

sealed interface Shape permits Circle, Rectangle {}
record Circle(Point centre, double radius) implements Shape {}
record Rectangle(Point topLeft, double width, double height) implements Shape {}
record Point(double x, double y) {}

String classify(Shape shape) {
    return switch (shape) {
        case Circle(Point(var x, var y), var r) when r > 100 ->
            "Large circle centred at (" + x + ", " + y + ")";
        case Circle c -> "Circle with radius " + c.radius();
        case Rectangle(var topLeft, var w, var h) when w == h ->
            "Square at " + topLeft;
        case Rectangle r -> "Rectangle " + r.width() + "x" + r.height();
    };
}

Nested destructuring like Circle(Point(var x, var y), var r) reaches directly into the record graph in a single pattern, which in real domain models (nested value objects, event payloads) removes several lines of manual accessor calls per branch.

Watch out. Guarded patterns (when) are evaluated in source order, and unlike a plain sealed-type switch, adding a guard means the compiler can no longer guarantee exhaustiveness purely from the type hierarchy — you are back to needing a catch-all case if the guards don't cover every value of a type. Always double-check exhaustiveness manually when mixing guards into an otherwise sealed switch.

2.4 Virtual Threads and Project Loom in Depth

Virtual threads are, for most enterprise Java teams, the single most consequential JDK feature since generics. Finalised in Java 21, they let ordinary, simple, blocking-style Java code scale to extremely high levels of concurrency without the complexity of reactive programming.

2.4.1 The Problem Virtual Threads Solve

Traditional Java concurrency maps one platform thread to one OS thread, and OS threads are expensive — typically megabytes of stack space each, with context-switching overhead that limits realistic pool sizes to hundreds or low thousands of threads. This is why "thread-per-request" servers historically hit a wall under high concurrency, pushing teams toward reactive stacks (WebFlux, RxJava) that decouple logical work from OS threads at the cost of much harder-to-read, harder-to-debug code (callback chains, operator soup, thread-hopping stack traces).

A virtual thread is a lightweight thread managed by the JVM rather than the OS. Millions can exist concurrently, because they only consume an OS thread ("carrier thread") while actively running CPU instructions; when a virtual thread blocks on I/O, the JVM unmounts it from its carrier thread, freeing that carrier to run other virtual threads, and remounts it (potentially on a different carrier) when the I/O completes.

// Traditional platform thread per request — limited by OS thread cost
ExecutorService platformPool = Executors.newFixedThreadPool(200);

// Virtual thread per request — scales to hundreds of thousands of concurrent tasks
ExecutorService virtualPool = Executors.newVirtualThreadPerTaskExecutor();

List<String> accountIds = fetchAccountIdsForReconciliation(); // e.g. 50,000 accounts

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<ReconciliationResult>> futures = accountIds.stream()
        .map(id -> executor.submit(() -> reconcileAccount(id))) // blocking DB/HTTP calls inside
        .toList();

    for (Future<ReconciliationResult> future : futures) {
        ReconciliationResult result = future.get(); // blocks the virtual thread, not the carrier
        recordResult(result);
    }
}

The code above is ordinary, blocking Java — no operators, no reactive types — yet it can comfortably issue tens of thousands of concurrent blocking calls (database queries, HTTP calls to downstream services) because each blocked virtual thread costs the JVM almost nothing while waiting.

2.4.2 Virtual Threads in Spring Boot

From Spring Boot 3.2 onward (and as a mature default in Spring Boot 4, covered in Chapter 3), enabling virtual threads for an entire Spring MVC application is a single property:

spring.threads.virtual.enabled=true

With this enabled, each incoming HTTP request is handled on its own virtual thread, and ordinary blocking Spring MVC controller code — JPA repository calls, RestClient calls to other services — gets dramatically higher throughput under concurrent load without any code changes.

2.4.3 When Virtual Threads Are Not the Answer

Important nuance. Virtual threads solve thread exhaustion under I/O-bound concurrency. They do not help with:
  • CPU-bound work — if your bottleneck is computation, not waiting, more virtual threads just contend for the same finite CPU cores.
  • Code with long synchronized blocks around blocking calls — prior to full "pinning" fixes, a virtual thread executing inside a synchronized block while blocking can pin its carrier thread, temporarily behaving like a platform thread. Prefer java.util.concurrent.locks.ReentrantLock over synchronized for code paths that block while holding a lock.
  • Native code / synchronized JNI calls that block without cooperating with the virtual thread scheduler.
For CPU-bound parallelism, you still want a bounded platform-thread pool sized close to the number of CPU cores, or the Vector API (Section 2.7) for data-parallel numerical work.
UK Job Market Tip. "When would you not use virtual threads?" is a strong signal question UK interviewers use to separate candidates who've read a blog post from candidates who understand the model. The synchronized-pinning caveat above is the single most useful fact to have ready.

2.5 Structured Concurrency

Structured concurrency (finalised as a stable feature moving through Java 21–25 previews) addresses a different problem: even with virtual threads making tasks cheap, coordinating related concurrent tasks — cancelling siblings when one fails, propagating errors sensibly, avoiding thread leaks — was still manual and error-prone using raw ExecutorService and CompletableFuture composition.

Response handleOrder(String orderId) throws InterruptedException, ExecutionException {
    try (var scope = StructuredTaskScope.open(StructuredTaskScope.Joiner.awaitAllSuccessfulOrThrow())) {

        var inventory = scope.fork(() -> inventoryClient.checkStock(orderId));
        var pricing   = scope.fork(() -> pricingClient.calculateTotal(orderId));
        var fraud     = scope.fork(() -> fraudClient.assessRisk(orderId));

        scope.join(); // waits for all forks; cancels siblings automatically on first failure

        return new Response(inventory.get(), pricing.get(), fraud.get());
    }
}

The critical property here is the parent–child relationship: the three forked subtasks are scoped to the try-with-resources block, cannot outlive it, and if any subtask throws, the others are cancelled automatically rather than continuing to run and leak resources. This gives concurrent code the same reasoning discipline as structured, single-threaded code — hence the name.

Best practice. Reach for structured concurrency whenever you're fanning out to multiple independent downstream calls to assemble a single response (a very common enterprise pattern — aggregating several microservice calls). Reach for plain virtual threads with an executor when tasks are independent and don't need coordinated cancellation, such as the bulk reconciliation example in Section 2.4.1.

2.6 Project Valhalla: Value Objects and Primitive Classes

Project Valhalla is the longest-running of the JDK's structural projects, and by 2026 its value-object model is available through preview features on Java 25 and later, with production readiness expected across the following LTS cycle. It addresses a cost that has existed since Java 1.0: every object, however small and immutable, carries an object header and lives behind a pointer, which means a large array of small wrapper objects (think a million Point or Money instances) pays for memory indirection and cache misses that a genuinely flat, inlined layout would avoid.

// Illustrative Valhalla-style value class (preview syntax, subject to change across previews)
value class Point {
    double x;
    double y;

    Point(double x, double y) {
        this.x = x;
        this.y = y;
    }
}

A value class has no object identity: two instances with the same field values are indistinguishable, there is no meaningful == beyond value equality, and the JVM is free to store instances inline — inside an array, or inside another object — rather than as separate heap allocations linked by references. For workloads that currently use primitive arrays plus manual indexing to avoid object overhead (a common, ugly optimisation in performance-sensitive financial code), value objects promise the readability of real objects with the memory layout of primitives.

Where this matters in UK enterprise work. High-frequency trading systems, risk calculation engines, and large in-memory analytics workloads are the workloads that most benefit from Valhalla. If you work in a UK investment bank's trading or risk technology division, tracking Valhalla's progress toward production readiness is directly relevant to your roadmap; for most CRUD-oriented enterprise services, it is good context to have but rarely a day-to-day concern yet.

2.7 The Vector API for Data-Parallel Computation

The Vector API expresses computations — such as adding two large arrays element-wise, or computing dot products — in a way that the JIT compiler can translate into CPU SIMD (Single Instruction, Multiple Data) instructions, processing multiple values per CPU cycle instead of one.

static final VectorSpecies<Float> SPECIES = FloatVector.SPECIES_PREFERRED;

void addArrays(float[] a, float[] b, float[] result) {
    int upperBound = SPECIES.loopBound(a.length);
    int i = 0;
    for (; i < upperBound; i += SPECIES.length()) {
        var va = FloatVector.fromArray(SPECIES, a, i);
        var vb = FloatVector.fromArray(SPECIES, b, i);
        va.add(vb).intoArray(result, i);
    }
    // Handle the remaining elements that don't fill a full vector lane
    for (; i < a.length; i++) {
        result[i] = a[i] + b[i];
    }
}

For UK enterprise teams, the realistic use cases are numerically heavy workloads that currently justify calling out to native libraries or a separate Python service: risk calculations, embedding pre/post-processing around the AI features covered in Chapter 5, and large-scale numerical analytics. The Vector API lets that computation stay in Java, in the same process, under the same observability and deployment model as the rest of the service.

2.8 Foreign Function & Memory API

The Foreign Function & Memory API (finalised in Java 22) replaces the old, unsafe, and painful Java Native Interface (JNI) for calling native libraries and working with off-heap memory. It is directly relevant whenever an enterprise system needs to call a native library — a legacy risk-calculation library, a specialised cryptography module, or a native machine-learning runtime.

try (Arena arena = Arena.ofConfined()) {
    Linker linker = Linker.nativeLinker();
    SymbolLookup stdlib = linker.defaultLookup();

    MethodHandle strlen = linker.downcallHandle(
        stdlib.find("strlen").orElseThrow(),
        FunctionDescriptor.of(ValueLayout.JAVA_LONG, ValueLayout.ADDRESS));

    MemorySegment cString = arena.allocateUtf8String("Hello from native code");
    long length = (long) strlen.invoke(cString);
    System.out.println("Length: " + length);
}

The Arena abstraction ties the lifetime of off-heap memory to a well-defined scope, closing a long-standing safety gap where manual native memory management in Java was a common source of native crashes and memory leaks.

2.9 Collections, Streams and Gatherers

The Stream API itself is unchanged in spirit since Java 8, but Stream Gatherers (finalised in Java 24) add a genuinely new capability: custom intermediate stream operations, filling a long-standing gap where the built-in operations (map, filter, reduce, and the various collectors) couldn't express certain useful transformations, such as sliding windows or stateful deduplication, without dropping into an ugly, imperative escape hatch.

List<List<Transaction>> slidingWindows = transactions.stream()
    .gather(Gatherers.windowSliding(3))
    .toList();

// Fixed-size, non-overlapping batches — useful for batch-processing downstream calls
List<List<Transaction>> batches = transactions.stream()
    .gather(Gatherers.windowFixed(100))
    .toList();

3.3 REST APIs with Spring MVC and Virtual Threads

With virtual threads enabled, a perfectly ordinary, blocking Spring MVC controller now scales the way a reactive controller used to require WebFlux to achieve:

@RestController
@RequestMapping("/api/v1/accounts")
class AccountController {

    private final AccountService accountService;

    AccountController(AccountService accountService) {
        this.accountService = accountService;
    }

    @GetMapping("/{accountNumber}")
    ResponseEntity<AccountResponse> getAccount(@PathVariable String accountNumber) {
        return accountService.findByAccountNumber(accountNumber)
            .map(account -> ResponseEntity.ok(AccountResponse.from(account)))
            .orElseGet(() -> ResponseEntity.notFound().build());
    }

    @PostMapping
    ResponseEntity<AccountResponse> openAccount(@Valid @RequestBody OpenAccountRequest request) {
        Account created = accountService.open(request.sortCode(), request.initialDeposit());
        return ResponseEntity
            .created(URI.create("/api/v1/accounts/" + created.accountNumber()))
            .body(AccountResponse.from(created));
    }

    @PostMapping("/{accountNumber}/transactions")
    ResponseEntity<TransactionResponse> postTransaction(
            @PathVariable String accountNumber,
            @Valid @RequestBody PostTransactionRequest request) {
        var transaction = accountService.postTransaction(accountNumber, request.amount(), request.type());
        return ResponseEntity.ok(TransactionResponse.from(transaction));
    }
}

record OpenAccountRequest(
        @Pattern(regexp = "\\d{2}-\\d{2}-\\d{2}") String sortCode,
        @DecimalMin("0.00") BigDecimal initialDeposit) {}

record PostTransactionRequest(
        @DecimalMin(value = "0.01") BigDecimal amount,
        TransactionType type) {}

record AccountResponse(String accountNumber, String sortCode, BigDecimal balance, AccountStatus status) {
    static AccountResponse from(Account account) {
        return new AccountResponse(account.accountNumber(), account.sortCode(), account.balance(), account.status());
    }
}

Notice records used throughout for request and response shapes, and Bean Validation annotations (@Pattern, @DecimalMin) applying directly to record components — validation and immutable data modelling compose cleanly.

3.4 Data Access: Spring Data JPA, R2DBC, and Testcontainers

For the ledger example, a traditional relational, JPA-backed repository remains the right choice — financial ledgers need strong transactional guarantees, and Spring Data JPA on top of virtual threads gives you blocking, easy-to-reason-about repository code without needing R2DBC's reactive complexity:

interface AccountRepository extends JpaRepository<AccountEntity, Long> {
    Optional<AccountEntity> findByAccountNumber(String accountNumber);
}

@Entity
@Table(name = "accounts")
class AccountEntity {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(unique = true, nullable = false)
    private String accountNumber;

    private String sortCode;
    private BigDecimal balance;

    @Enumerated(EnumType.STRING)
    private AccountStatus status;

    @Version
    private long version; // optimistic locking — essential for concurrent balance updates

    protected AccountEntity() {} // required by JPA

    // constructor, getters/setters omitted for brevity
}
Watch out. The @Version field enabling optimistic locking is not optional decoration in a ledger system — without it, two concurrent transactions against the same account can silently overwrite each other's balance update under Spring's default isolation settings. Combined with virtual threads potentially issuing far more concurrent requests than your old platform-thread pool ever allowed, skipping optimistic (or explicit pessimistic) locking is a bug that will surface in production far sooner than it used to.

3.5 Validation, Error Handling, and Problem Details (RFC 9457)

Rather than letting exceptions leak inconsistent stack-trace-shaped responses, centralise error handling using @RestControllerAdvice and Spring's built-in ProblemDetail support:

@RestControllerAdvice
class ApiExceptionHandler {

    @ExceptionHandler(AccountNotFoundException.class)
    ProblemDetail handleNotFound(AccountNotFoundException ex) {
        var problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setTitle("Account not found");
        problem.setType(URI.create("https://api.example.co.uk/errors/account-not-found"));
        return problem;
    }

    @ExceptionHandler(InsufficientFundsException.class)
    ProblemDetail handleInsufficientFunds(InsufficientFundsException ex) {
        var problem = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_ENTITY, ex.getMessage());
        problem.setTitle("Insufficient funds");
        return problem;
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail handleValidation(MethodArgumentNotValidException ex) {
        var problem = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Validation failed");
        problem.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
            .map(err -> err.getField() + ": " + err.getDefaultMessage())
            .toList());
        return problem;
    }
}

This produces standard, machine-parseable application/problem+json responses that any downstream consumer — a mobile app team, a partner integration, a monitoring tool — can handle consistently, rather than every team inventing its own error envelope.

3.7 Building a Financial Ledger API — Worked Example

Bringing the chapter together, the service layer below composes records, sealed result types, and validation into a complete transaction-posting flow:

sealed interface TransactionResult permits Posted, Rejected {}
record Posted(Transaction transaction, BigDecimal newBalance) implements TransactionResult {}
record Rejected(String reason) implements TransactionResult {}

@Service
class AccountService {

    private final AccountRepository accountRepository;

    AccountService(AccountRepository accountRepository) {
        this.accountRepository = accountRepository;
    }

    @Transactional
    TransactionResult postTransaction(String accountNumber, BigDecimal amount, TransactionType type) {
        AccountEntity account = accountRepository.findByAccountNumber(accountNumber)
            .orElseThrow(() -> new AccountNotFoundException(accountNumber));

        BigDecimal signedAmount = type == TransactionType.DEBIT ? amount.negate() : amount;
        BigDecimal newBalance = account.getBalance().add(signedAmount);

        if (newBalance.signum() < 0 && account.getStatus() != AccountStatus.OVERDRAFT_APPROVED) {
            return new Rejected("Transaction would exceed authorised limit");
        }

        account.setBalance(newBalance);
        accountRepository.save(account); // optimistic lock via @Version protects concurrent updates

        var transaction = new Transaction(UUID.randomUUID().toString(), accountNumber, amount, type, Instant.now());
        return new Posted(transaction, newBalance);
    }
}

The controller from Section 3.3 can now pattern-match on the sealed TransactionResult to produce the right HTTP response, tying together everything from Chapter 2 and this chapter into one coherent, idiomatic flow:

@PostMapping("/{accountNumber}/transactions")
ResponseEntity<?> postTransaction(@PathVariable String accountNumber, @Valid @RequestBody PostTransactionRequest request) {
    TransactionResult result = accountService.postTransaction(accountNumber, request.amount(), request.type());
    return switch (result) {
        case Posted(var transaction, var balance) ->
            ResponseEntity.ok(new TransactionResponse(transaction.id(), balance));
        case Rejected(var reason) ->
            ResponseEntity.unprocessableEntity().body(ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_ENTITY, reason));
    };
}

4.1 Containerising Java Applications

Three broad approaches dominate UK enterprise practice for producing a container image from a Spring Boot application, each with different trade-offs.

4.1.1 Spring Boot Buildpacks (Cloud Native Buildpacks)

./mvnw spring-boot:build-image -Dspring-boot.build-image.imageName=ledger-api:1.0.0

4.1.2 Hand-Written Multi-Stage Dockerfile

FROM eclipse-temurin:25-jdk-alpine AS build

WORKDIR /app
COPY --from=build /app/target/ledger-api-*.jar app.jar

AI-Powered Java Applications

By 2026, "experience integrating AI/LLM features" appears in a meaningful share of UK backend job specifications that have nothing to do with an AI/ML team's core remit — it has become an ordinary enterprise Java capability, the way "REST API" or "message queue" was a decade ago. 5.1 The AI Engineering Landscape for Java Developers

Three capabilities recur across almost every enterprise AI feature, regardless of the specific use case:

  • Chat/completion calls to a hosted or self-hosted model provider.
  • Retrieval-Augmented Generation (RAG) — grounding model responses in your organisation's own documents or data, rather than relying on the model's training data alone, which matters enormously for factual accuracy and for keeping proprietary/regulated data out of a third party's training pipeline.
  • Tool calling / agents — letting the model decide to invoke your own application code (look up an account balance, check claim status, raise a support ticket) as part of producing a response.

Spring AI 2.0 provides a consistent abstraction over all three, so switching model providers, vector stores, or observability backends is largely a configuration change rather than a rewrite.

5.3 Building a Retrieval-Augmented Generation (RAG) Pipeline

RAG grounds a model's response in specific, retrieved documents rather than trusting its training data — essential when answers must reflect your organisation's actual policies, product terms, or case history, and essential for reducing hallucination risk in regulated contexts.

@Service
class PolicyDocumentIngestionService {

    private final VectorStore vectorStore;

    PolicyDocumentIngestionService(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
    }

    void ingest(Resource policyDocument) {
        var reader = new TikaDocumentReader(policyDocument);
        var splitter = new TokenTextSplitter();
        List<Document> chunks = splitter.apply(reader.get());
        vectorStore.add(chunks);
    }
}

@Service
class PolicyQaService {

    private final ChatClient chatClient;
    private final VectorStore vectorStore;

    PolicyQaService(ChatClient.Builder builder, VectorStore vectorStore) {
        this.vectorStore = vectorStore;
        this.chatClient = builder.build();
    }

    String answer(String question) {
        List<Document> relevant = vectorStore.similaritySearch(
            SearchRequest.query(question).withTopK(4));

        String context = relevant.stream()
            .map(Document::getContent)
            .collect(Collectors.joining("\n---\n"));

        return chatClient.prompt()
            .system("Answer only using the provided policy context. If the context doesn't contain the answer, say so.")
            .user(u -> u.text("Context:\n" + context + "\n\nQuestion: " + question))
            .call()
            .content();
    }
}

Spring AI's VectorStore abstraction supports numerous backends — PostgreSQL with pgvector, Redis, Elasticsearch, and dedicated vector databases — chosen the way you'd choose any other data store, based on your existing infrastructure and operational familiarity rather than AI-specific novelty.

Watch out. The instruction "answer only using the provided context" reduces hallucination but does not eliminate it — models can still misstate or over-generalise from retrieved context. For any customer-facing regulated use case (insurance claims guidance, financial advice, benefits eligibility), retrieved-and-generated answers should be treated as a drafting aid for a human reviewer, not an autonomous final answer, until your organisation has validated accuracy and put appropriate sign-off controls in place.

5.4 Tool Calling and Building Agents

Tool calling lets a model decide, based on the conversation, to invoke one of your application's own methods — checking a real account balance rather than guessing, for instance — and then incorporate the result into its response.

@Service
class AccountLookupTools {

    private final AccountService accountService;

    AccountLookupTools(AccountService accountService) {
        this.accountService = accountService;
    }

    @Tool(description = "Look up the current balance for a UK bank account by account number")
    BigDecimal getBalance(String accountNumber) {
        return accountService.findByAccountNumber(accountNumber)
            .map(Account::balance)
            .orElseThrow(() -> new AccountNotFoundException(accountNumber));
    }
}

@Service
class BankingAssistantService {

    private final ChatClient chatClient;

    BankingAssistantService(ChatClient.Builder builder, AccountLookupTools tools) {
        this.chatClient = builder
            .defaultTools(tools)
            .build();
    }

    String respond(String customerMessage) {
        return chatClient.prompt()
            .user(customerMessage)
            .call()
            .content();
    }
}

With @Tool-annotated methods registered on the ChatClient, a customer asking "what's the balance on account 12345678?" causes the model to call getBalance directly against your real, authoritative data — the model never has to (and should never be trusted to) know or guess the actual figure.

Employers are typically not looking for machine-learning research skills here — they want Java developers who can wire a model provider up to existing, well-tested application services safely, exactly as shown above.

5.6 Observability and Guardrails for LLM-Backed Features

AI-backed features need the same operational discipline as any other production dependency, plus a few AI-specific concerns:

  • Latency and cost monitoring — model calls are typically the slowest and most expensive operation in a request path; instrument them explicitly via Micrometer/OpenTelemetry (Chapter 6) rather than treating them as an opaque black box.
  • Input/output guardrails — validating that user input doesn't attempt prompt injection against your system instructions, and that model output doesn't leak system prompts or context it shouldn't (particularly important when RAG context may include sensitive customer data).
  • Fallback behaviour — a model provider outage should degrade gracefully (a clear "assistant unavailable, here's how to contact us directly" message), not surface as a raw 500 error, using the same resilience patterns covered in Chapter 6.
GDPR note. Any RAG pipeline or tool-calling flow that passes customer personal data to a third-party model provider is a data processing activity under UK GDPR, and needs the same data processing agreements, data residency consideration, and privacy-by-design review as any other third-party integration handling personal data. This is covered in full in Chapter 7, but it's worth flagging here: "add an AI feature" is not exempt from your organisation's normal data protection review process just because it's new and exciting.

Microservices, Resilience & Observability

A single well-built Spring Boot service, however modern, is not an architecture. This chapter covers what changes once the ledger API from Chapter 3 has siblings — services it depends on, and services that depend on it — and the failure modes that only appear once a request's success depends on multiple independently-deployed processes, often over an unreliable network.

6.1 Service Decomposition Strategies

The most common and most damaging microservices mistake in UK enterprise estates is decomposing services along technical layers (a "database service," a "validation service") rather than business capabilities. Domain-Driven Design's notion of a bounded context remains the most reliable heuristic: a service should own a cohesive piece of business capability — accounts, payments, customer identity — with its own data store, deployed and scaled independently of the others.

Best practice. Before splitting a monolith, map out which pieces of data change together and which pieces of functionality are deployed and scaled at different rates. Services that must share a database transaction to remain consistent are a strong signal they belong together, at least initially — premature decomposition based on org-chart boundaries rather than actual coupling is a frequently cited cause of costly microservices rework in UK enterprise post-mortems.

6.2 Resilience Patterns: Circuit Breakers, Retries, Bulkheads

Once the ledger API calls out to, say, a fraud-scoring service, that dependency's failure or slowness becomes the ledger API's problem too, unless explicitly contained. Resilience4j, integrated cleanly with Spring Boot, provides the standard toolkit:

@Service
class FraudCheckClient {

    private final RestClient restClient;

    FraudCheckClient(RestClient.Builder builder) {
        this.restClient = builder.baseUrl("http://fraud-service").build();
    }

    @CircuitBreaker(name = "fraudService", fallbackMethod = "fallbackAssessment")
    @Retry(name = "fraudService")
    @TimeLimiter(name = "fraudService")
    FraudAssessment assess(String transactionId) {
        return restClient.get()
            .uri("/assess/{id}", transactionId)
            .retrieve()
            .body(FraudAssessment.class);
    }

    FraudAssessment fallbackAssessment(String transactionId, Throwable t) {
        // Fail safe: flag for manual review rather than silently approving or hard-failing
        return new FraudAssessment(transactionId, RiskLevel.REQUIRES_MANUAL_REVIEW, "Fraud service unavailable");
    }
}

resilience4j:
  circuitbreaker:
    instances:
      fraudService:
        sliding-window-size: 20
        failure-rate-threshold: 50
        wait-duration-in-open-state: 15s
  retry:
    instances:
      fraudService:
        max-attempts: 3
        wait-duration: 200ms
  timelimiter:
    instances:
      fraudService:
        timeout-duration: 2s

The circuit breaker stops hammering a struggling dependency once its failure rate crosses a threshold, failing fast (via the fallback) instead of piling up slow, doomed requests. The bulkhead pattern — isolating the thread/connection pool used for one downstream call from others — remains relevant even with virtual threads: it protects against one misbehaving dependency exhausting shared resources like an HTTP connection pool, even though thread exhaustion itself is far less of a concern than it was pre-Loom.

Watch out. A fallback that silently returns a "safe-looking" default (e.g. treating an unreachable fraud service as "no risk detected") can be actively dangerous in a financial context — it converts an infrastructure outage into a security control bypass. The fallback above deliberately routes to manual review rather than approving by default; always think through what your fallback value actually communicates downstream, not just whether it prevents an exception from propagating.

6.3 Event-Driven Architecture with Kafka

Where synchronous calls create tight coupling and cascading failure risk, event-driven architecture via Kafka lets services communicate through durable, replayable event streams instead — a pattern extremely common in UK financial services for anything resembling a ledger, audit trail, or multi-step workflow.

@Service
class TransactionEventPublisher {

    private final KafkaTemplate<String, TransactionPostedEvent> kafkaTemplate;

    TransactionEventPublisher(KafkaTemplate<String, TransactionPostedEvent> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    void publish(Posted posted) {
        var event = new TransactionPostedEvent(
            posted.transaction().id(), posted.transaction().accountNumber(),
            posted.newBalance(), Instant.now());
        kafkaTemplate.send("transaction-posted", event.accountNumber(), event);
    }
}

@Component
class FraudMonitoringConsumer {

    @KafkaListener(topics = "transaction-posted", groupId = "fraud-monitoring")
    void onTransactionPosted(TransactionPostedEvent event) {
        // Independently, asynchronously assess the posted transaction for fraud patterns
        fraudPatternService.evaluate(event);
    }
}

Publishing the transaction-posted event decouples the ledger service completely from whatever downstream systems care about it — fraud monitoring, customer notifications, regulatory reporting — each consuming the same event stream independently, without the ledger service needing to know they exist.

6.5 API Gateways and Service Mesh

As service counts grow, cross-cutting concerns — authentication, rate limiting, TLS termination, routing — get centralised either at an API gateway (Spring Cloud Gateway, Kong, AWS API Gateway) sitting at the edge, or pushed down into a service mesh (Istio, Linkerd) operating at the network layer between every service.

  • API gateway: simpler to reason about, sufficient for most estates, handles north-south traffic (external clients into your services).
  • Service mesh: adds mutual TLS, fine-grained traffic policies, and observability for east-west traffic (service-to-service), at the cost of real operational complexity — generally only justified once an estate reaches a scale where manually managing service-to-service security and traffic policy becomes unworkable.
Best practice. Don't reach for a service mesh because a conference talk made it sound essential. Most UK enterprise Java estates — even fairly large ones — run perfectly well with a solid API gateway plus Resilience4j-based resilience patterns and OpenTelemetry tracing, and only adopt a service mesh once mTLS-everywhere or fine-grained traffic shaping becomes a genuine, named requirement.

Security, Compliance & Testing

Security and compliance are not a chapter you bolt on after building the system — but they are, realistically, the point in most books where they get covered separately, and this one is no exception, because the UK's regulated industries treat them as distinct, auditable disciplines with their own named owners. 7.1 Application Security Fundamentals (OWASP Top 10 in 2026)

The OWASP Top 10 remains the standard reference for the most common and most damaging web application vulnerability classes. For Java developers building Spring Boot services, the entries that recur most often in real audits are:

  • Broken access control — endpoints missing proper authorisation checks, or checks performed inconsistently across a service.
  • Injection — largely mitigated by default in Spring Data JPA/parameterised queries, but still possible via native queries built with string concatenation.
  • Security misconfiguration — default credentials, verbose error responses leaking stack traces, permissive CORS configuration left over from local development.
  • Vulnerable and outdated components — the single most common finding in dependency-scanning audits of Java codebases, addressed in Section 7.5.
  • Identification and authentication failures — weak session handling, missing rate limiting on authentication endpoints.
Best practice. Never construct SQL, including native/JPQL queries, via string concatenation of user input, even for "internal" admin tooling — internal tools are a disproportionately common source of injection vulnerabilities precisely because they're assumed to be low-risk and reviewed less carefully.

7.2 Spring Security 7 and OAuth2/OIDC

Spring Security 7 continues the lambda-based configuration style established in Spring Security 6, and integrates cleanly with OAuth2/OpenID Connect for delegating authentication to an identity provider — the standard approach for UK enterprise services rather than hand-rolled username/password authentication.

@Configuration
@EnableWebSecurity
class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/v1/accounts/**").hasAuthority("SCOPE_accounts:read")
                .requestMatchers(HttpMethod.POST, "/api/v1/accounts/**").hasAuthority("SCOPE_accounts:write")
                .anyRequest().authenticated())
            .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()))
            .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS));
        return http.build();
    }
}

7.3 GDPR and UK Data Protection in Practice

UK GDPR (the retained, UK-specific version of the EU regulation, enforced by the ICO) shapes several concrete engineering practices that appear repeatedly across regulated UK employers:

7.3.1 Data Minimisation and Purpose Limitation

API responses and logs should never include personal data beyond what the specific operation requires. A common finding in UK data protection audits is logging entire request/response bodies for debugging purposes, inadvertently persisting personal data in log aggregation systems with far weaker access controls than the primary database.

// Avoid: logs the entire request including any personal data it carries
log.info("Received request: {}", request);

// Prefer: log identifiers needed for correlation, not the personal data itself
log.info("Processing account opening for sortCode={}, correlationId={}",
    maskSortCode(request.sortCode()), correlationId);

7.3.2 Right to Erasure and Data Subject Access Requests

Systems handling personal data need a defensible, tested mechanism for both retrieving all data held about an individual (a Data Subject Access Request, or DSAR) and, where legally permitted, erasing it. In practice this usually means every service owning personal data implements a documented, testable "export my data" and "erase my data" capability, often orchestrated centrally rather than left to each team to interpret independently.

7.3.3 Data Residency

Many UK public sector and financial services contracts specify that personal data must remain within the UK (or UK/EU) at rest and, for some engagements, in transit. This directly affects cloud region selection (Chapter 4 and 9), and — as flagged in Chapter 5 — which AI model providers can legitimately be used for features that process personal data.

GDPR note. None of the above constitutes legal advice, and a real compliance programme requires input from your organisation's data protection officer and legal team. What's engineering-actionable is the discipline: know what personal data a service touches, minimise what you log and retain, and be able to answer "how would we fulfil a DSAR against this service" before it's asked of you in an audit rather than during one.

Performance, Migration & Modernisation

Much of the highest-value Java work in the UK enterprise market is not greenfield development — it's modernising a system that has been running, and earning its keep, since well before Java 8 reached end of life. This chapter covers how the JVM actually manages memory and garbage collection today, how to measure performance properly rather than guessing, and a practical playbook for migrating a legacy estate from Java 8/11 to 21/25 without a disruptive big-bang rewrite.

8.1 JVM Memory Model and Modern Garbage Collectors

The default garbage collector has changed materially since the Java 8 era, and the choice of collector is one of the highest-leverage JVM tuning decisions available to a team.

CollectorIntroducedCharacteristicsTypical Fit
Parallel GCLong-standing default pre-Java 9Optimises for throughput; noticeable pause timesBatch jobs where pause time doesn't matter
G1 GCDefault since Java 9Balances throughput and pause time; region-basedGeneral-purpose default for most enterprise services
ZGCProduction-ready Java 15+, generational ZGC Java 21+Sub-millisecond pause times even on very large heapsLatency-sensitive services, large heaps (tens of GB+)
ShenandoahProduction-ready Java 15+ (Red Hat-led)Low pause times, works well on smaller heaps tooAlternative to ZGC, particularly on Red Hat-based platforms
# Explicitly select generational ZGC for a latency-sensitive trading/risk service
java -XX:+UseZGC -XX:+ZGenerational -Xmx16g -jar risk-engine.jar
Best practice. G1 remains a perfectly reasonable default for the majority of CRUD-style enterprise services, and switching collectors without measuring first is a common source of wasted tuning effort. Reach for ZGC specifically when you have measured, real pause-time problems on a large heap — for example, a risk calculation engine holding tens of gigabytes of market data in memory where even G1's typically-short pauses are unacceptable.

8.2 Profiling and Benchmarking with JFR and JMH

Java Flight Recorder (JFR), built into the JDK since Java 11 and free to use in production (unlike its commercial predecessor), is the standard first step for diagnosing a real performance issue rather than guessing at one:

# Record a 60-second profile with minimal overhead, safe to run in production
java -XX:StartFlightRecording=duration=60s,filename=recording.jfr -jar ledger-api.jar

The resulting recording, opened in JDK Mission Control, shows CPU hot paths, allocation rates, GC pause distribution, and lock contention — usually enough to identify whether a reported slowdown is a database query, a hot allocation path, GC pressure, or lock contention, before making any code change.

For micro-benchmarking specific methods (rather than whole-application profiling), the Java Microbenchmark Harness (JMH) remains the standard, because naive hand-rolled "time it with System.nanoTime()" benchmarks are notoriously unreliable due to JIT warm-up and dead-code elimination:

@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.MICROSECONDS)
@State(Scope.Thread)
public class MoneyAdditionBenchmark {

    private final Money a = new Money(new BigDecimal("100.00"), Currency.getInstance("GBP"));
    private final Money b = new Money(new BigDecimal("50.00"), Currency.getInstance("GBP"));

    @Benchmark
    public Money addMoney() {
        return a.plus(b);
    }
}
Watch out. Never trust a benchmark you wrote by hand with System.currentTimeMillis() around a loop — the JIT compiler can eliminate "dead" code that computes a result nothing uses, and warm-up effects mean the first thousand iterations of any benchmark are measuring compilation, not steady-state performance. JMH exists specifically to avoid these traps, and any performance claim in a design document or PR description should be backed by a JMH benchmark or a JFR recording, not intuition.

8.3 Migrating from Java 8 to 21/25: A Practical Playbook

Migrating a genuinely legacy Java 8 codebase rarely fails because of language syntax changes — it fails because of unmaintained dependencies, removed APIs, and module system friction. A realistic, staged playbook:

8.3.1 Stage One: Java 8 to Java 11

  • Remove any dependency on Java EE modules bundled with Java 8 but removed from the JDK in Java 11 (JAXB, JAX-WS, CORBA, Java Activation) — these need to become explicit Maven/Gradle dependencies.
  • Replace any use of internal sun.* or com.sun.* APIs, which the module system increasingly restricts access to.
  • Run the build with --release 11 and resolve any compilation failures before touching runtime behaviour.

8.3.2 Stage Two: Java 11 to Java 17

  • Audit for reliance on the default (unrestricted) module path behaviour that strong encapsulation in later JDKs may break, particularly reflection-heavy frameworks and libraries doing bytecode manipulation.
  • Upgrade Mockito, Hibernate, and any bytecode-manipulation-based testing/mocking libraries to versions compatible with the newer bytecode/module rules — this is consistently the largest source of migration friction in practice.

8.3.3 Stage Three: Java 17 to Java 21/25

  • Adopt records and sealed types incrementally for new code, rather than attempting a wholesale rewrite of existing DTOs — the two styles coexist without friction.
  • Enable virtual threads (spring.threads.virtual.enabled=true) in a non-production environment first, and load-test for any behaviour that depends on ThreadLocal assumptions tied to a small, fixed platform-thread pool, since virtual threads change the relationship between "thread" and "concurrent request" fundamentally.
  • Review any code using synchronized blocks around blocking I/O for the carrier-thread pinning issue discussed in Chapter 2, replacing with ReentrantLock where it matters for throughput.
UK Job Market Tip. "Legacy modernisation" roles — explicitly advertised as such — are a significant, steady segment of the UK Java market, particularly in financial services and public sector, and typically pay well precisely because the work requires both deep technical judgement and the patience to do it incrementally and safely. Being able to describe a staged migration plan like the one above, rather than "just upgrade the JDK version," is a strong differentiator for these roles.

8.4 Modernising Monoliths: The Strangler Fig Pattern

For a large legacy monolith, a full rewrite is almost always the wrong choice — it takes too long, freezes feature delivery, and carries enormous risk of reintroducing bugs the old system quietly fixed over years of production use. The Strangler Fig pattern, named for the vine that gradually grows around and eventually replaces its host tree, migrates functionality incrementally instead:

  1. Place a routing layer (an API gateway, or a simple reverse proxy) in front of the monolith.
  2. Identify one bounded, well-understood piece of functionality (e.g. account balance lookups) and reimplement it as a new, independently deployed service.
  3. Route just that functionality's traffic to the new service, while everything else continues to hit the monolith unchanged.
  4. Repeat, one capability at a time, until the monolith has been "strangled" down to nothing, or to a core that genuinely belongs together.
Best practice. Always migrate the functionality with clearest boundaries and lowest risk first, not the most technically interesting piece. Early wins build organisational confidence in the migration approach and reveal integration challenges (shared database tables, hidden coupling) while the blast radius of a mistake is still small.

DevOps, CI/CD & Deployment

Writing good Java is only half the job in a modern enterprise team; the other half is getting it into production safely, repeatedly, and quickly. This chapter builds a complete pipeline for the ledger API — from commit to a running Kubernetes deployment on a UK cloud region — and covers the progressive delivery techniques that let teams ship frequently without betting the whole user base on every release.

9.1 CI/CD Pipelines with GitHub Actions and GitLab CI

Both GitHub Actions and GitLab CI dominate UK enterprise usage, generally following whichever platform already hosts the organisation's source code. A representative GitHub Actions pipeline for the ledger API:

name: ledger-api-ci
on:
  push:
    branches: [main]
  pull_request:

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '25'
          cache: maven
      - name: Run unit and integration tests
        run: ./mvnw verify
      - name: Generate SBOM and scan dependencies
        run: ./mvnw org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom
      - name: Build container image
        run: ./mvnw spring-boot:build-image -Dspring-boot.build-image.imageName=ledger-api:${{ github.sha }}
      - name: Push to registry
        run: |
          echo "${{ secrets.REGISTRY_PASSWORD }}" | docker login registry.example.co.uk -u ci --password-stdin
          docker push registry.example.co.uk/ledger-api:${{ github.sha }}

  deploy-staging:
    needs: build-and-test
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - name: Deploy to staging Kubernetes cluster
        run: kubectl set image deployment/ledger-api ledger-api=registry.example.co.uk/ledger-api:${{ github.sha }}
Best practice. Fail the build on any critical/high-severity CVE found during the SBOM/dependency scan step, and treat this as a non-negotiable gate rather than an informational report — a scan result nobody acts on provides audit-trail comfort without actual security benefit.

9.4 Progressive Delivery: Blue-Green and Canary Releases

Deploying a new version directly to 100% of production traffic is a bet with no graceful way to hedge. Two complementary techniques reduce that risk:

9.4.1 Blue-Green Deployment

Two complete environments ("blue," currently live, and "green," the new version) run side by side; traffic is switched from blue to green atomically once the green environment is verified healthy, with the ability to switch back instantly if problems appear.

9.4.2 Canary Releases

A new version is rolled out to a small percentage of traffic first (say 5%), monitored closely against error rate and latency metrics (using the OpenTelemetry instrumentation from Chapter 6), and only progressively rolled out further once it proves healthy:

apiVersion: split.smi-spec.io/v1alpha3
kind: TrafficSplit
metadata:
  name: ledger-api-canary
spec:
  service: ledger-api
  backends:
    - service: ledger-api-stable
      weight: 90
    - service: ledger-api-canary
      weight: 10
Where this matters for UK enterprise risk appetite. Financial services and public sector deployments, given the cost of an incident affecting real money movements or citizen services, near-universally favour canary releases with automated rollback triggered on error-rate or latency degradation, over a straight blue-green switch with no gradual exposure. Being able to describe this preference, and why, is a strong, concrete talking point that goes beyond simply naming the tools.

Case Studies & Real-World Projects

This chapter ties together every preceding chapter through three composite case studies, modelled on the shape of real UK enterprise and public sector systems rather than any single named organisation. Each case study states the business context, the architectural decisions, and — most usefully for interview preparation — the trade-offs a competent team would actually have debated before settling on its approach.

10.1 A Retail Bank Payments Platform

Context

A retail bank needs to modernise its Faster Payments-adjacent transaction processing, currently running on an ageing Java 8 monolith backed by a single large Oracle database, toward a resilient, horizontally scalable platform capable of handling regulatory reporting, fraud checks, and real-time balance updates without a single point of failure.

Architecture Decisions

  • Strangler Fig migration (Chapter 8): payment initiation extracted first as an independent Spring Boot 4 service, since it has the clearest boundary and lowest coupling to the rest of the monolith's reporting logic.
  • Event-driven core (Chapter 6): every state change (initiated, authorised, settled, failed) published as a Kafka event, giving fraud monitoring, regulatory reporting, and customer notification services independent, decoupled consumers of the same event stream.
  • Virtual threads throughout (Chapter 2): given the I/O-bound nature of calling core banking, fraud, and clearing systems, virtual threads let the team keep straightforward, blocking Spring MVC code while comfortably absorbing peak transaction volumes (e.g. pay-day spikes) without reactive complexity.
  • Canary deployment with automated rollback (Chapter 9): given the direct financial consequence of a bad release, every deployment ships to 5% of traffic first, monitored against error rate and settlement-latency service-level objectives before progressing.
  • ZGC on the risk/fraud scoring service (Chapter 8): this specific service holds a large in-memory model of recent transaction patterns and is latency-sensitive enough that GC pause time was a measured, real problem under G1, justifying the move.
UK Job Market Tip. Interview questions modelled on this case study often probe the reasoning, not just the technology list: "why event-driven rather than synchronous calls between these services?" and "why extract payment initiation first, rather than fraud scoring?" are far more revealing questions than "have you used Kafka?" — prepare to explain trade-offs, not just name tools.

10.2 A UK Government Citizen Portal

Context

A government department needs a citizen-facing portal for checking benefit eligibility and submitting applications, subject to strict accessibility standards (WCAG, aligned with GOV.UK Design System conventions), GDPR requirements around sensitive personal and financial data, and highly seasonal traffic patterns around policy announcements and deadlines.

Architecture Decisions

  • GraalVM native-image-compiled eligibility-checking service (Chapter 4): chosen specifically because this citizen-facing entry point experiences the sharpest, least predictable traffic spikes, and fast cold starts under autoscaling materially reduce both cost during quiet periods and latency during demand surges.
  • Strict data minimisation in logging (Chapter 7): given the sensitivity of benefits and financial data, structured logging deliberately excludes personal data fields, logging only correlation IDs and non-identifying status information.
  • OpenTelemetry tracing end-to-end (Chapter 6): essential both for operational reliability during demand spikes and for the auditability that government digital services are expected to demonstrate to oversight bodies.
  • OAuth2/OIDC integration with GOV.UK One Login (conceptually, per Chapter 7): citizen identity verification delegated to the appropriate central government identity service rather than the portal implementing its own authentication.
  • Kubernetes deployment across UK regions (Chapter 9) with data residency requirements satisfied by keeping all citizen data within UK-based cloud regions.

10.3 A Consulting-Delivered Data Platform for the NHS Supply Chain

Context

A consultancy is engaged to build a data platform aggregating supply chain data (stock levels, procurement, delivery tracking) across a large number of NHS trusts, replacing a fragmented set of spreadsheet-based reporting processes with a unified, near-real-time view.

Architecture Decisions

  • Microservices decomposed by bounded context (Chapter 6): separate services for stock-level ingestion, procurement-order tracking, and demand forecasting, each owned by a different delivery workstream within the consulting engagement, deployed and scaled independently.
  • AI-assisted anomaly detection and summarisation (Chapter 5): a Spring AI-backed feature summarises unusual stock-level patterns for supply chain analysts, deliberately kept as a human-reviewed drafting aid given the operational sensitivity of clinical supply decisions, following the same human-in-the-loop principle as the claims-processing case study in Chapter 5.
  • Strict contract testing between ingestion and reporting services (Chapter 7): given that dozens of NHS trusts feed data into the platform with varying data quality and formats, contract tests catch breaking schema changes from any single trust's integration before they silently corrupt aggregate reporting.
  • Cost-conscious JVM sizing (Chapter 4): given public sector budget constraints, careful right-sizing of Kubernetes resource requests based on measured usage, rather than default over-provisioning, was an explicit, tracked cost-saving workstream in the engagement.

11.5 Contracting vs Permanent: IR35 Considerations

Contract Java work remains common in the UK, particularly for time-bounded modernisation projects (Chapter 8) of the kind large financial services and public sector organisations frequently commission. Since the 2021 off-payroll working (IR35) reforms extended responsibility for employment status determination to medium/large private-sector clients (mirroring rules already in place for public sector engagements since 2017), most genuine contracting arrangements for UK-based clients are now assessed and determined by the client organisation itself, and a meaningful share of contract Java roles are consequently offered "inside IR35" — taxed broadly as employment income despite the contracting structure.

Not financial or legal advice. IR35 status determination depends on the specific facts of an engagement and current HMRC guidance, and genuinely qualified advice should come from an accountant or IR35 specialist familiar with your circumstances, not a programming book. What's useful to know going in: ask about IR35 status explicitly before accepting a contract role, understand whether the day rate quoted is inside or outside IR35 (since take-home pay differs substantially between the two), and factor that into any comparison against a permanent role's base salary.
