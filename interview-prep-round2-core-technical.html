Q1JAVA CORE

Explain SOLID principles with a real example from your work.

SOLID is five design principles that keep object-oriented code maintainable as it grows:

  • S — Single Responsibility: a class should have one reason to change. E.g. an OrderService shouldn't also handle sending emails — that belongs in a NotificationService.
  • O — Open/Closed: classes should be open for extension, closed for modification. E.g. adding a new payment type should mean adding a new class implementing a PaymentStrategy interface, not editing a big switch statement in existing code.
  • L — Liskov Substitution: a subclass should be usable anywhere its parent type is expected without breaking behavior.
  • I — Interface Segregation: prefer several small, specific interfaces over one large one, so classes don't implement methods they don't need.
  • D — Dependency Inversion: depend on abstractions, not concrete implementations — which is exactly what Spring's dependency injection encourages by default.

Real example: on a project with multiple payment providers, I refactored a growing if/else block choosing payment logic into a PaymentStrategy interface with one implementation per provider, injected via Spring. Adding a new provider later meant adding one new class — zero changes to existing, tested code. That's Open/Closed and Dependency Inversion working together.

Q2JAVA 8+

What Java 8+ features do you use regularly, and why?

Streams — for declarative collection processing instead of manual loops:

List<String> activeEmails = users.stream()
    .filter(User::isActive)
    .map(User::getEmail)
    .collect(Collectors.toList());

Optional — to make "this might not have a value" explicit in method signatures, instead of relying on null checks scattered through calling code:

public Optional<User> findById(String id) {
    return userRepository.findById(id);
}
// caller:
userRepository.findById(id)
    .map(User::getEmail)
    .orElseThrow(() -> new UserNotFoundException(id));

Lambdas and method references — mainly for concise functional interfaces (Comparator, Runnable, custom @FunctionalInterface types) and stream operations, as shown above.

var (Java 10, but relevant here) — for local type inference where the type is obvious from the right-hand side, improving readability without sacrificing type safety.

Common follow-up: "What's the risk of overusing streams?" — readability drops fast with deeply chained or nested streams, and debugging a stream pipeline is harder than stepping through a loop. I keep pipelines to 3–4 operations before breaking them into named intermediate variables or methods.
Q3COLLECTIONS

How does HashMap work internally? What's different in a ConcurrentHashMap?

HashMap stores entries in an array of buckets. A key's hashCode() is run through an internal hash function to pick a bucket index; entries in the same bucket (hash collisions) are stored as a linked list. Since Java 8, if a single bucket's linked list grows beyond a threshold (8 entries, with the table large enough), it's converted into a red-black tree, turning worst-case lookup from O(n) to O(log n) for that bucket. Resizing happens when the map's size exceeds capacity × loadFactor (default 0.75) — the table doubles and all entries are rehashed.

HashMap is not thread-safe — concurrent modification can corrupt the bucket structure (historically even caused infinite loops during resize under concurrent writes).

ConcurrentHashMap solves this without locking the whole map. Instead of one lock for the entire structure (like the older, now-discouraged Hashtable), it uses fine-grained locking at the bucket/node level (in modern versions, via CAS operations and synchronized blocks only on the specific bin being modified). This means multiple threads can read and write to different parts of the map concurrently with minimal contention, while reads are largely lock-free.

Common follow-up: "When would you still need external synchronization with ConcurrentHashMap?" — for compound operations that need to be atomic together, e.g. "check if absent, then insert" across multiple map calls; use computeIfAbsent or merge instead, since those are atomic single operations.
Q4CONCURRENCY

Explain synchronized vs. Lock vs. using a concurrent collection for thread safety.

synchronized — the simplest option; a built-in monitor lock on an object or method. Simple to use, automatically released even if an exception is thrown, but inflexible — no timeout, no ability to check "is this locked," and one thread waiting can't be interrupted.

public synchronized void deduct(BigDecimal amount) {
    if (balance.compareTo(amount) >= 0) {
        balance = balance.subtract(amount);
    }
}

ReentrantLock (from java.util.concurrent.locks) — more flexible: supports tryLock() with a timeout, interruptible locking, and fairness policies. Requires manual unlocking in a finally block, which is more error-prone if forgotten.

private final ReentrantLock lock = new ReentrantLock();

public void deduct(BigDecimal amount) {
    lock.lock();
    try {
        if (balance.compareTo(amount) >= 0) {
            balance = balance.subtract(amount);
        }
    } finally {
        lock.unlock();
    }
}

Concurrent collections (ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue) — the preferred choice when the problem is really "safe shared collection access," since they handle synchronization internally and are heavily optimized, usually outperforming a hand-rolled synchronized wrapper.

My default: reach for a concurrent collection or the java.util.concurrent utilities (Atomic classes, ExecutorService) first; drop to synchronized for simple cases; use ReentrantLock only when I specifically need its extra capabilities like tryLock or interruptibility.

Q5SPRING INTERNALS

Explain the Spring Bean lifecycle and the difference between singleton and prototype scope.

Lifecycle (simplified): Spring instantiates the bean → injects dependencies → calls @PostConstruct (or InitializingBean.afterPropertiesSet()) → the bean is ready for use → on container shutdown, calls @PreDestroy (or DisposableBean.destroy()) for cleanup, for singleton-scoped beans.

@Component
public class CacheWarmer {
    @PostConstruct
    public void init() {
        // pre-load cache after dependencies are injected
    }

    @PreDestroy
    public void cleanup() {
        // release resources on shutdown
    }
}

Singleton (Spring's default) — one instance per Spring container, shared across the entire application. Efficient, but means the bean must be stateless or thread-safe, since concurrent requests share the same instance.

Prototype — a new instance is created every time the bean is requested from the container. Useful for beans that hold request-specific mutable state, but Spring does not manage the full lifecycle for prototype beans — @PreDestroy is not called automatically; cleanup is the caller's responsibility.

Common follow-up: "What happens if you inject a prototype bean into a singleton?" — by default, the prototype bean is only created once, at injection time, and then reused like a singleton within that parent bean — which usually isn't what people expect. The fix is either method injection or injecting an ObjectFactory/Provider to fetch a fresh instance on each use.
Q6TRANSACTIONS

How does @Transactional work, and what does propagation mean?

@Transactional wraps a method call in a database transaction using Spring's AOP proxying — when you call an annotated method, you're actually calling a proxy that starts a transaction, invokes your method, then commits on success or rolls back on a runtime exception (checked exceptions don't trigger rollback by default).

@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);
    inventoryService.reserveStock(order); // same transaction
}

Propagation controls how a transactional method behaves when called from within another transactional method:

  • REQUIRED (default) — join the existing transaction if one exists, or start a new one.
  • REQUIRES_NEW — always start a new, independent transaction, suspending the current one. Useful for logging or audit writes that should persist even if the outer transaction rolls back.
  • NESTED — starts a nested transaction (via savepoints) that can roll back independently without rolling back the outer transaction.
Common gotcha to mention proactively: @Transactional doesn't work when called from within the same class (self-invocation bypasses the proxy), and it only rolls back on unchecked exceptions by default — checked exceptions need rollbackFor = Exception.class explicitly.
Q7DATABASE / JPA

What is the N+1 query problem, and how do you fix it in JPA/Hibernate?

The N+1 problem happens when fetching a list of N parent entities triggers one query for the list, then N additional queries — one per parent — to lazily load each parent's related child entities. For example, fetching 50 orders and then accessing order.getItems() on each one, with lazy loading, results in 1 + 50 = 51 queries instead of 2.

// Triggers N+1: one query for orders, then one per order for items
List<Order> orders = orderRepository.findAll();
orders.forEach(o -> o.getItems().size()); // lazy load fires here, per order

Fixes:

  • JOIN FETCH in JPQL — pulls related entities in the same query: SELECT o FROM Order o JOIN FETCH o.items.
  • @EntityGraph — declaratively specify which associations to eagerly fetch for a specific query, without changing the entity's default fetch type globally.
  • Batch fetching — @BatchSize or Hibernate's hibernate.default_batch_fetch_size, which groups the "N" lazy-load queries into a smaller number of IN (...) queries instead of one-per-parent.

In practice, I catch these during development by enabling SQL logging (show-sql plus a tool like p6spy or Hibernate statistics) and watching for repeated near-identical queries in a loop — that's the tell-tale sign of N+1.

Q8MICROSERVICES RESILIENCE

How do you make microservices resilient to downstream failures? Explain the circuit breaker pattern.

When Service A calls Service B synchronously and B is slow or down, without protection, A's threads pile up waiting on B — which can exhaust A's own thread pool and cause A to fail too, cascading the outage. Resilience patterns exist to contain that.

Circuit breaker (implemented with Resilience4j in modern Spring Boot, after Hystrix's deprecation) wraps calls to a downstream service and tracks failure rate. It has three states:

  • Closed — calls pass through normally; failures are counted.
  • Open — once failures exceed a threshold, the circuit "trips": further calls fail immediately (or return a fallback) without even attempting the network call, giving the downstream service room to recover.
  • Half-Open — after a wait period, a limited number of trial calls are allowed through; if they succeed, the circuit closes again, otherwise it reopens.
@CircuitBreaker(name = "inventoryService", fallbackMethod = "fallbackStock")
public StockDto checkStock(String productId) {
    return inventoryClient.getStock(productId);
}

public StockDto fallbackStock(String productId, Throwable t) {
    return StockDto.unavailable(productId); // graceful degradation
}

I'd usually pair this with a timeout (so a single slow call doesn't hang indefinitely) and a retry with backoff for transient failures — but retries need care in combination with circuit breakers, since retrying too aggressively can itself overwhelm a struggling downstream service.

Q9REACT PERFORMANCE

Explain React's reconciliation process and how you'd optimize unnecessary re-renders.

React keeps a virtual DOM — a lightweight in-memory representation of the UI tree. When state changes, React re-renders the component (calls the function again) to produce a new virtual DOM tree, then diffs it against the previous tree to figure out the minimal set of real DOM changes needed, rather than re-rendering the whole page. This diffing process is what's called reconciliation.

A component re-renders when its own state changes, its props change, or its parent re-renders — and by default, a parent re-rendering re-renders all its children too, even if their props didn't actually change. That's the usual source of unnecessary re-renders in larger component trees.

Optimization tools:

  • React.memo — wraps a component so it only re-renders if its props actually changed (shallow comparison).
  • useMemo — memoizes an expensive computed value so it's only recalculated when its dependencies change.
  • useCallback — memoizes a function reference itself, which matters because passing a new inline function as a prop on every render defeats React.memo on the child receiving it.
const ExpensiveList = React.memo(function ExpensiveList({ items, onSelect }) {
  return items.map(item => <Row key={item.id} item={item} onSelect={onSelect} />);
});

function Parent({ items }) {
  const handleSelect = useCallback((id) => { /* ... */ }, []);
  return <ExpensiveList items={items} onSelect={handleSelect} />;
}
Common follow-up: "Should you wrap everything in memo/useMemo/useCallback?" — no; each adds its own small overhead and complexity. I reach for these only after profiling (React DevTools Profiler) shows a genuine re-render cost, not as a default habit.
Q10SYSTEM DESIGN (LIGHT)

Walk me through designing a URL shortener at a high level.

Core requirements: given a long URL, return a short unique code; given that code, redirect to the original URL. At scale, reads (redirects) vastly outnumber writes (new short URLs).

API shape:

POST /api/urls        { "longUrl": "https://..." } -> { "shortCode": "aZ9k2" }
GET  /{shortCode}     -> 302 redirect to the original long URL

Generating the short code: two common approaches —

  • Base62 encoding of an auto-incrementing ID — simple, guaranteed unique, but reveals creation order and requires a centralized ID generator (or a distributed ID scheme like Snowflake if sharded).
  • Hash the long URL (e.g. MD5) and take the first 6-7 characters — no central counter needed, but requires collision handling (check if the code's already taken; if so, append a salt and rehash).

Storage: a key-value store (short code → long URL) is a natural fit — Redis or DynamoDB for very high read throughput, or a relational DB with a heavy caching layer in front if the team already runs one. Given reads dominate, I'd put a cache (Redis) in front of whatever persistent store is used, since the same popular short links get hit repeatedly.

Scaling considerations I'd raise:

  • Read-heavy traffic → cache aggressively, and consider a CDN or edge redirect layer for very high-traffic links.
  • ID generation must not become a bottleneck or single point of failure — a distributed ID generator, or hash-based generation, avoids a single counter.
  • Analytics (click counts) shouldn't block the redirect path — log asynchronously (e.g. publish an event) rather than writing synchronously on every redirect request.
How I'd open this in an interview: clarify scale (how many URLs/redirects per day) and whether custom aliases or expiry are needed before diving into a design — that framing signals structured thinking, which usually matters more than the specific answer.

In a core technical round, interviewers often care less about a perfect answer and more about how you reason when they push back — so after each answer here, mentally rehearse one likely follow-up question and how you'd handle not immediately knowing the answer.
