Q3TECHNICAL — ARCHITECTURE

What's the difference between monolithic and microservices architecture, and when would you choose microservices?

A monolith is a single deployable unit — all modules (user management, orders, payments, etc.) run in one process, share one codebase, and typically one database. It's simpler to develop, test, and deploy early on, but as the application grows, deployments get riskier, scaling is all-or-nothing, and teams start stepping on each other's code.

Microservices split the application into independently deployable services, each owning its own data and business capability, communicating over the network (REST, gRPC, or messaging). Each service can be scaled, deployed, and even written in a different tech stack independently.

I'd choose microservices when:

  • Different parts of the system have very different scaling needs (e.g. a search service under heavy load vs. a low-traffic admin service)
  • Multiple teams need to ship independently without coordinating a single release
  • The domain has clear bounded contexts that map naturally to separate services

I'd stick with a monolith (or a "modular monolith") for smaller teams or early-stage products, since microservices add real operational overhead — service discovery, distributed tracing, network latency, and eventual consistency — that isn't worth paying for until the team and traffic actually need it.

Q4TECHNICAL — SPRING BOOT

How does Spring Boot simplify enterprise Java development? What is auto-configuration?

Traditional Spring required a lot of XML or Java-based configuration — defining beans, data sources, view resolvers, and so on by hand. Spring Boot removes most of that by providing sensible defaults and starter dependencies (spring-boot-starter-web, spring-boot-starter-data-jpa, etc.) that pull in exactly the libraries you need for a given concern, pre-wired to work together.

Auto-configuration is the mechanism behind this. At startup, Spring Boot inspects what's on the classpath and what beans already exist in the context, then conditionally configures beans you'd otherwise have to define manually. For example, if spring-boot-starter-data-jpa and a JDBC driver are on the classpath, Spring Boot automatically configures a DataSource, an EntityManagerFactory, and a transaction manager — unless you've already defined your own, in which case yours takes precedence.

@SpringBootApplication
public class OrderServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrderServiceApplication.class, args);
    }
}

That single @SpringBootApplication annotation combines @Configuration, @EnableAutoConfiguration, and @ComponentScan — which is what gives you a working application with almost no boilerplate.

Q5TECHNICAL — SPRING CORE

Explain Dependency Injection in Spring, and the difference between @Component, @Service, @Repository, and @Controller.

Dependency Injection is the pattern where an object's dependencies are provided to it from the outside — by the Spring container — rather than the object creating them itself. Spring manages the lifecycle of these objects (called beans) and wires them together based on annotations or configuration, which makes code loosely coupled and much easier to unit test, since dependencies can be mocked.

@Service
public class OrderService {
    private final OrderRepository orderRepository;

    // Constructor injection — preferred over field injection
    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
}

On the stereotype annotations — functionally, @Component, @Service, @Repository, and @Controller all do the same thing: they mark a class as a Spring-managed bean, discoverable via component scanning. The difference is semantic and, in a couple of cases, functional:

  • @Component — the generic stereotype; any Spring-managed bean.
  • @Service — marks a service-layer class holding business logic. Purely semantic, but improves readability.
  • @Repository — marks a data access layer class. This one is functional too: Spring wraps repository beans with exception translation, converting database-specific exceptions into Spring's unified DataAccessException hierarchy.
  • @Controller / @RestController — marks a web layer class handling HTTP requests. @RestController combines @Controller and @ResponseBody, so return values are serialized directly into the HTTP response body (typically as JSON).
Q6TECHNICAL — MICROSERVICES

How do microservices communicate with each other? Explain synchronous vs. asynchronous communication.

Synchronous communication — typically REST over HTTP, or gRPC for lower-latency internal calls. The calling service sends a request and waits for a response before continuing. It's simple to reason about and debug, but it creates tight runtime coupling — if the downstream service is slow or down, the caller is blocked or fails too, and failures can cascade across the system.

@GetMapping("/orders/{id}")
public OrderDto getOrder(@PathVariable String id) {
    InventoryDto inventory = inventoryClient.checkStock(id); // blocks here
    return orderService.buildOrder(id, inventory);
}

Asynchronous communication — typically event-driven, using a message broker like Kafka or RabbitMQ. A service publishes an event ("OrderPlaced") without waiting for consumers to process it; other services subscribe and react independently. This decouples services in time — the publisher doesn't need the consumer to be available at that exact moment — and improves resilience and scalability, at the cost of eventual consistency and more complex debugging (tracing a request across async hops needs proper distributed tracing, like Sleuth/Zipkin or OpenTelemetry).

In practice, I lean synchronous REST for calls where the caller genuinely needs an immediate answer (e.g. checking real-time stock availability), and event-driven messaging for anything that's fundamentally a "notify and move on" operation (e.g. sending a confirmation email after an order is placed, updating a reporting service).

Q7TECHNICAL — DISTRIBUTED TRANSACTIONS

What is the Saga pattern, and why is it needed in microservices?

In a monolith, a multi-step operation (e.g. place an order, reserve inventory, charge payment) can be wrapped in a single ACID database transaction — if any step fails, everything rolls back. In microservices, each of those steps typically lives in a different service with its own database, so a single distributed transaction (two-phase commit) is usually avoided — it doesn't scale well and creates tight coupling between services.

The Saga pattern solves this by breaking the operation into a sequence of local transactions, each in its own service, where each step publishes an event that triggers the next step. If a step fails partway through, the saga runs compensating transactions to undo the effects of the steps that already succeeded — rather than rolling back a single distributed transaction.

  • Choreography-based saga — each service listens for events and reacts, publishing its own event in turn. No central coordinator; simpler for small workflows, but can get hard to trace as the number of services grows.
  • Orchestration-based saga — a central orchestrator service explicitly tells each service what to do next and handles failure/compensation logic centrally. Easier to monitor and reason about for complex workflows, at the cost of a more central dependency.

Example: order placed → inventory reserved → payment charged. If payment fails, the saga triggers a compensating action to release the reserved inventory, rather than trying to lock both databases in one transaction.

Q8TECHNICAL — REACT

How do React hooks like useState and useEffect work, and why did hooks replace class components?

Before hooks, state and lifecycle logic (like fetching data on mount) only existed in class components, using this.state and lifecycle methods like componentDidMount. This meant related logic often got scattered across multiple lifecycle methods, and reusing stateful logic between components required patterns like higher-order components or render props, which added a lot of nesting.

Hooks let function components hold state and side effects directly:

function OrderStatus({ orderId }) {
  const [status, setStatus] = useState('loading');

  useEffect(() => {
    fetch(`/api/orders/${orderId}/status`)
      .then(res => res.json())
      .then(data => setStatus(data.status));
  }, [orderId]); // re-run only when orderId changes

  return <span>{status}</span>;
}

useState gives a piece of state and a setter function; calling the setter triggers a re-render with the new value. useEffect runs side effects (data fetching, subscriptions, manual DOM work) after render, and re-runs only when values in its dependency array change — replacing componentDidMount, componentDidUpdate, and componentWillUnmount (via the cleanup function it can return) in one API.

Hooks won out because they let you extract and reuse stateful logic through custom hooks, keep related logic together instead of split across lifecycle methods, and avoid the confusion around this binding that class components required.

Q9TECHNICAL — SECURITY

How do you secure a Spring Boot REST API? Walk me through a JWT-based authentication flow.

I'd use Spring Security as the foundation, with JWT (JSON Web Tokens) for stateless authentication — which fits naturally with a microservices architecture, since no service needs to maintain server-side session state.

The flow:

  • The client sends credentials to an authentication endpoint (or an identity provider, if using OAuth2).
  • The server validates credentials and issues a signed JWT — a token containing claims (user ID, roles, expiry) signed with a secret or private key, so it can't be tampered with undetected.
  • The client stores the token and sends it in the Authorization: Bearer <token> header on subsequent requests.
  • A Spring Security filter intercepts each request, validates the token's signature and expiry, and if valid, populates the security context with the user's identity and roles — no database lookup needed for authentication itself.
  • Method or endpoint-level authorization then checks roles/permissions, e.g. @PreAuthorize("hasRole('ADMIN')").
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    return http
        .csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()))
        .build();
}

For inter-service calls in a microservices setup, I'd also look at propagating the token (or a service-to-service token via OAuth2 client credentials) so downstream services can independently validate the caller's identity, rather than trusting the network boundary alone.

Q10BEHAVIORAL

Describe a challenging technical problem you solved — ideally around scalability or performance.

On one AEM-based platform I worked on, page load times degraded significantly as content volume grew — a component was making repeated synchronous calls to a backend service to resolve related content on every render, which was fine at low volume but didn't scale as editors added more content.

What I did:

  • Profiled the request path and found the component was resolving the same related-content lookups on every single page render, with no caching layer.
  • Introduced a caching layer (leveraging AEM's dispatcher cache for the rendered output, plus an in-memory cache for the backend lookups themselves) so repeated lookups within a short window were served from cache instead of hitting the backend each time.
  • Batched what had been N individual backend calls into a single bulk call where possible, cutting network round-trips significantly.

The result was a meaningful drop in average page render time, and it taught me to think about caching and request batching much earlier in design — a lesson I carry directly into how I design Spring Boot services now, particularly around avoiding N+1 query problems and adding appropriate caching (Spring's @Cacheable, or a dedicated layer like Redis) before it becomes a production issue rather than after.
